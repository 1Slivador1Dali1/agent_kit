# Шаги 7–8. Сдача, коммит, удаление планов

## 7. Сдача

Писать пользователю в этом виде. Пустой класс не упоминать. Секции ниже не заменять списком файлов.

```markdown
### Что реализовано
- Мелкая: …
- Средняя: …
- Большая: …

### Как проверить
1. …

### Сверка с общим планом
- [x] пункт — чем подтверждено
- [ ] пункт — расхождение

### Ревью
- PASS или ISSUES — одна строка
```

Если правила репозитория требуют отчёт «было → стало», добавить его секции следом. «Что реализовано» и «Как проверить» остаются.

`status: await-user`. Коммит в этом же ответе не делать. Ход закончить.

## 8. Подтверждение

Слово подтверждения при `await-user`: `подтверждаю`, `принято`, `всё успешно`, `коммить`, `можно коммитить`.

Тогда, и только тогда:

1. Параллельно посмотреть статус git, дифф и последние сообщения коммитов. Стиль сообщения взять из истории: 1–2 предложения, зачем изменение.
2. В коммит не класть секреты (`.env`, ключи, токены). Если такие файлы попали в дифф — остановиться и сказать о них, не коммитить.
3. Не менять git config. Не пушить. Не делать `--no-verify` и `--no-gpg-sign`. Не делать `--amend`. Не делать force push. Интерактивный `git add -i` и `git rebase -i` не использовать.
4. Сообщение передать через HEREDOC.
5. Если хук отклонил коммит — править причину и создать новый коммит. Каталог прогона при неудачном коммите не удалять.

Push не делать.

Удалять только каталог этого прогона. В коммит его не добавлять, если этого каталога ещё не было в git.

- Каталога нет в HEAD: удалить его после коммита с кодом 0.
- Каталог уже в HEAD: удаление включить в тот же коммит. Если коммит не прошёл — вернуть каталог и оставить планы на диске.

После успешного коммита: `status` уже негде хранить, в ответе — хеш коммита, сообщение и что каталог прогона удалён. `git status` после коммита проверить.

Неясное «ну вроде да» — одно уточнение, коммит не делать, статус оставить `await-user`.
